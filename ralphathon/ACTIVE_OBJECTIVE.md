GS건설의 데이터센터 후보 부지 검토를 돕는 “여기 DC 돼요?”를 완결된 웹서비스로 구현하고, 2026-09-22 오전 10:00(KST)까지 검증·Vercel 배포·해커톤 발표자료 준비를 마쳐라.

## 1. 문제와 사용자
주 사용자는 GS건설에서 데이터센터 개발·사업검토를 담당하는 실무자다. 후보지를 제안받을 때 전력·인허가·재해·주변 현황을 각각 찾아 비교하고 보고해야 하는 부담을 줄인다. 확인된 제약, 미확인 조건, 다음 확인사항을 같은 형식으로 정리하여 후속 조사할 후보를 추리고 내부 협의에 활용하게 한다.

## 2. 완성할 웹서비스
저장소 `https://github.com/seungminyi-byte/Camp_It_Ralph`의 `prototype`과 현행 지침·코드를 확인하고, 기존 계산 엔진·데이터·유효한 기능을 계승한다.

- **메인:** 해결하는 문제, 사용 대상, 대표 결과 화면과 ‘부지 검토 시작’ 버튼을 제공한다. Paces(https://www.paces.com/)를 주된 레퍼런스로 삼아 정보 구성과 시각적 흐름을 설계한다.
- **프로젝트 소개:** 기획 배경, 기존 업무의 불편, 사용 절차, 주요 기능, 데이터 출처와 활용 범위를 설명한다.
- **팀 소개:** 아래 이야기와 제공한 사진으로 팀의 경험과 제작 동기를 전달한다.
- **검토 앱:** 주소 검색/지도 선택 → 기본 검토 → 선택적 상세조건 입력 → 최대 4곳 비교 → 보고서·A4 PDF까지 연결한다. 내부 사업정보나 AI 없이도 기본 검토와 보고서를 사용할 수 있게 한다. 지도 화면은 Felt(https://felt.com/product)를 주된 레퍼런스로 삼아 지도·레이어·정보 패널·조작 도구를 설계한다.

공통 내비게이션·푸터·디자인을 적용하고, 소개 페이지와 앱 사이의 이동, 직접 접속, 새로고침, 뒤로가기가 정상 작동하게 한다. 앱을 벗어나 소개 페이지를 보더라도 진행 중인 검토를 불필요하게 잃지 않게 한다.

### 팀 소개: 우리가 계약서를 덮고 지도를 편 이유
팀명은 ‘캠핑왕 랄프’다. 이번 해커톤을 위해 구성한 팀으로, 다음 이야기를 중심으로 소개한다.

> 우리는 GS건설 국내법무팀에서 함께 일하는 변호사들입니다. 데이터센터 관련 분쟁 자문과 계약 검토를 하며, 부지를 고르는 첫 선택이 이후 사업에 얼마나 큰 영향을 미치는지 체감했습니다. 분쟁이 생기기 전에, 부지 선택 단계에서 위험을 미리 살펴볼 수 있다면 어떨까요? 그 생각을 직접 도구로 만들고 싶어 해커톤에 참여했습니다. ‘여기 DC 돼요?’는 그렇게 시작됐습니다.

이 이야기를 통해 변호사가 계약서를 덮고 지도를 펼친 이유를 전달한다. 현재 사내 법무관리시스템을 대체할 새로운 법무시스템 개발을 Codex와 진행하고 있으며, 소송 서면·법률 의견서 작성을 위한 플러그인과 스킬을 직접 만들어 업무에 활용한다는 경험도 자연스럽게 소개한다.

진행 중인 개발을 완료된 성과로 표현하거나 이름·경력·사건 내용을 추측하지 않는다.

제공한 사진 001의 정면 단체사진과 002·003의 뒷모습 사진을 화면 크기와 이야기 흐름에 맞게 선별 활용한다. 원본을 보존하고 인물을 왜곡하지 않으며, 반응형 크롭·이미지 용량·대체텍스트를 점검한다.

공개 유사 서비스·GitHub 프로젝트의 사용 흐름과 구조를 비교하고 실제 필요한 부분을 적용한다. 디렉터리는 기존 빌드·배포를 유지하면서 기능과 책임에 맞게 정리한다. https://getdesign.md 에서 보조 디자인 후보 3개를 검토·토의하되, 메인은 Paces, 지도는 Felt라는 방향을 유지하고 기존 GS 오렌지를 주색으로 사용한다.

## 3. 완료 확인 기준
- **업무 흐름:** 메인 진입부터 주소 검토·조건 변경·후보 추가/삭제·4곳 제한·비교·보고서 출력까지 필수 시나리오를 정하고 Playwright와 실제 브라우저에서 모두 통과시킨다. 버튼 동작뿐 아니라 결과 내용과 상태 변화를 확인한다.
- **계산 정확성:** 구현과 독립적으로 기대값을 정하고 엔진·화면·비교·PDF의 수치와 단위를 대조한다. 대표 회귀는 연면적 30,000㎡·용적률 200%·건폐율 50%·4층의 최소 대지 15,000㎡, 평균 차입잔액 1,000억원·연 6%·12개월의 금융비용 60억원이다. 미입력과 명시적 0을 구별하고 불완전한 비용을 최저비용으로 표시하지 않는다.
- **자료와 보고서:** 주요 판단에서 출처·기준일·입력 가정·미확인을 확인할 수 있어야 한다. 첫 장에 후보 위치, 주요 제약, 중요한 미확인 사항, 비교 요약과 다음 확인사항을 담는다. 실제 A4 PDF 전 페이지의 잘림·겹침·누락을 확인한다.
- **오류와 AI:** 빈 입력·잘못된 숫자·자료 결측·지원하지 않는 위치·조회 지연/실패·AI 중단/빈 응답을 검증한다. 늦게 도착한 이전 조회 결과가 현재 후보를 덮어쓰지 않아야 한다. 입력·근거 변경 시 기존 AI 의견을 무효화하고, AI 의견의 수치·주요 주장을 제공 근거와 대조한다. 실패한 조회를 ‘제약 없음’으로 해석하지 않는다.
- **사용성과 응답:** 390/768/1440px에서 핵심 업무를 완료할 수 있어야 한다. 검색·목록을 통해 지도 조작 없이도 주요 정보를 확인하게 한다. 키보드·포커스·입력 라벨·명암 대비를 직접 점검하고 주요 화면의 axe Critical·Serious 위반을 해소한다. 대표 입력과 실행환경을 정해 첫 검토 결과·비교 갱신·보고서 열기의 소요시간을 기록하고 병목을 개선한다. 외부 요청은 정한 제한시간 내 결과 또는 오류 상태로 전환하고 재시도할 수 있게 한다.
- **테스트와 보안:** 외부 API의 정상·오류·지연 응답을 고정한 회귀검사와 배포 후 실제 연결 검사를 구분한다. 타입 검사·린트·전체 테스트·데이터 검증·빌드를 통과한다. 공개 API의 잘못된 형식·과도한 입력·중복 요청, 외부자료와 AI 출력의 안전한 표시, 비밀키 노출을 점검한다. 발견한 취약점은 실제 사용 경로와 영향에 따라 조치한다.
- **재현성과 배포:** 새 폴더에서 문서만으로 설치·빌드·실행한다. 배포 커밋·Vercel Ready·실제 화면·핵심 API 본문을 확인하고 공개 링크를 비로그인 환경에서 검증한다.

## 4. 결과물과 발표자료
공개 웹서비스와 GitHub 저장소, 최대 5페이지 발표자료와 5분 발표 대본을 완성한다. 웹사이트 소개와 발표자료는 같은 문제 정의와 검증된 기능을 설명해야 한다.

실행 안내, 검증용 예제 입력, 실제 출력 PDF, 검증 결과, 기존 구현의 재사용 범위와 이번 변경 내용을 남긴다. 실제 주요 세션 JSONL과 추가 에이전트 로그를 보존하고, 비밀정보를 점검한 제출용 사본을 준비한다.

## 5. 판단 범위와 실행 방식
총괄 아래 기획·조사·자료정리·디자인·개발·보고서·테스트·검증·검수·수정·디버깅·보안·배포·발표자료·완료보고를 별도 에이전트에 맡긴다. 업무는 검수 가능한 산출물 단위로 세분화하고 작업마다 새 하위 에이전트에 필요한 문맥과 자료만 인계한다.

총괄 외 실행 에이전트는 기본적으로 한 번에 하나다. 이전 작업의 완료·검수·인계 후 다음 작업을 시작한다. 총 예상 소요가 15시간을 넘을 때만 근거를 기록하고 파일·의존성이 분리된 작업을 제한적으로 병렬화한다.

중요한 범위·설계·디자인 결정은 관련 에이전트가 순차적으로 대안과 반론을 검토하고 총괄이 결론을 기록한다. 일반적인 제품·기술 선택은 사용자에게 묻지 않고 결정한다.

모델은 사용 가능한 권한과 예산 안에서 **결과물의 품질을 최우선**으로 선택한다. 정확성·추론·코딩·도구 활용 능력을 우선하고 속도와 비용은 그다음에 고려한다. 핵심 설계·구현·검증에 더 적합한 고품질 모델이 지원되면 지정해 사용하고 실제 선택·위임을 기록한다.

코드·문서 수정, 검사, 작업 브랜치·PR을 통한 반영, 기존 GitHub·Vercel 권한 내 공개 배포를 수행한다. 신규 결제·권한 확대·파괴적 변경·대회 최종 제출은 별도 승인을 받는다.

## 6. 제약·검증 루프·종료
공개자료와 합성 검증 데이터를 사용하고 사내자료·비밀키를 공개하지 않는다. 기존 스택과 계산의 단일 기준, 사용자·팀원의 변경을 보존한다. 로그인·결제·협업 백엔드와 대규모 신규 데이터 수집은 범위에 넣지 않는다.

사실·가정·미확인을 구분하고 공급 가능량·인허가·사업 적합성이나 측정하지 않은 절감 효과를 단정하지 않는다. 필요한 출처·자료 한계와 “스크리닝 참고용, 한전 공식 검토·법률 판단 대체 불가”를 간결하게 표시한다.

GS·Team Attention의 행사 지침과 OpenAI 공식 Goal·Subagents 문서를 참고해 현재 환경에서 “기준 확인 → 작은 작업 → 실행 → 별도 검증 → 실패 수정 → 재검증 → 인계”를 반복한다. 목표 원문, 단계별 완료 조건, 결정, 증거, 남은 일은 `ralphathon/`에 유지한다.

계산·근거의 정확성, 핵심 업무 흐름, 실패 복구, 배포 안정성을 먼저 확보하고 소개 페이지와 발표자료를 완성한다. 필수 기준과 결과물을 모두 확인하면 종료한다. 완료 시각에 미충족 항목이 있으면 실패·미검증·제약을 명확히 보고하고 완료로 표시하지 않는다. 2026-09-22 오전 10:00(KST)에 목표가 미완료이면, 진행 중인 작업을 안전하게 정리하고 Goal을 일시정지한 뒤 달성·미달성 항목과 남은 일을 보고하라. 목표 변경은 이유를 기록하며, 검증 결과와 변경 영향에 따라 필요한 검사만 반복한다.
