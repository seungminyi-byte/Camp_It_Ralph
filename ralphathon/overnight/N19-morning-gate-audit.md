# N19 — 오전 검증 도구의 독립 오프라인 감사

2026-09-22 02:06 KST 기준 준비 도구 `N06/prepared-manifest-v4.json`을 검토했다. **실제 오전 관측은 수행하지 않았다.** 네트워크·Vercel/GitHub 명령·브라우저 실행·AI 추론은 모두 0회다. 이 감사는 제품 결함이나 현재 운영 장애를 새로 관측한 기록이 아니다.

N06을 수정하기 전에 확인해야 할 결함은 네 군이다. 배포 확인과 요청의 연결, 시각 범위, 조회 완결성·재해 응답 형식, 주변 후보의 숫자·ID·도형 검사가 해당한다. AI의 짧은 텍스트 분류를 보고서 품질로 승격하지 않는 수동 검수 경계는 유지됐다.

## 범위와 증거

- 루트와 저장소 `AGENTS.md`, 실행 런북·상태·결정·인계·목표 원문 및 N06 README를 적용했다. N06의 준비 상태, 09시 이후 한정 실행, 10시 하드 마감, 원본 보존을 기준으로 삼았다.
- `verify_release.py`, `live_api.py`, `browser.mjs`, `static.py`, `accept_basic_checks.py`, `probe_ai.py`, `correlate_probe.py`를 읽었다. 실제 실행한 소스 재생은 `live_api`, `accept_basic_checks`, `probe_ai`뿐이며, 나머지는 읽기 검토다.
- 총괄이 지정한 모델을 유지했고 N19 내부 모델 전환·추가 에이전트 위임은 없다. 복잡한 판정 경계의 정확성과 도구 적합성을 속도·비용보다 우선했다. 별도 모델 성능 실측은 하지 않았다.
- N06 기존 합성 fixture를 읽어 새 N19 fixture를 만들었다. 기존 총괄 4사례 전체를 반복하지 않고 새로운 고정 반례 13개와 구별에 필요한 통제 사례 3개를 재생했다. 이 중 기본 검증 13례는 12수락·1거절, AI 분류 3례는 모두 텍스트 분류만 남겼다. 시험 성공 횟수나 제품 789검사에 더하지 않는다.
- 수집기 코드 자체가 mock HTTP 본문을 읽고 raw 본문·SHA·JSON 기록을 생성했다. 수락기만 속이기 위해 서로 모순되는 본문과 해시를 만든 시험이 아니다. 브라우저·정적 결과는 종전 합성 fixture의 복사본이므로 이번에 브라우저·정적 파일의 실제 내용을 다시 검증한 것은 아니다.
- 실행 중 `urlopen`은 고정 mock, 시계는 고정값, subprocess와 socket 연결은 금지 함수로 바꿨다. 소스 문자열 치환은 절대 ROOT를 N19 임시 루트로 옮기는 한 가지뿐이다. 모든 시험 입출력은 `work/overnight/N19/` 안이다.
- N06 39파일의 시작·종료 바이트/SHA-256을 보존 검사했다. v4 manifest의 12개 선언도 모두 원본과 일치했다. 제품·원본 근거·N06·outputs·설정·git은 수정하지 않았다.

실행기·고정결과·입력 보존표·최종 봉인표는 각각 루트 기준 `work/overnight/N19/audit_offline.py`, `offline-results.json`, `input-preservation.json`, `owned-manifest.json`이다. 감사 산출물은 연구용 합성자료이며 전달본이나 오전 성공 근거로 사용하지 않는다. 개별 `cases/`의 `mock-request-audit.json`과 `*.replay.json`에 실제 실행 함수·고정 시각·결과를 구분했다.

## F01 — 확인한 배포와 나중 요청의 배포가 연결되지 않는다 (P2)

위치: `work/overnight/N06/probe_ai.py:18-26,30-33,63`, `live_api.py:12,40`, `static.py:10,19`, `browser.mjs:7-9`.

`verify_release`는 그 시점의 공개 별칭 READY와 정확한 SHA의 GitHub deployment 성공을 실제로 대조한다. 그러나 후속 수집기는 가변 공개 별칭으로 요청하고, 요청을 처리한 배포를 확인하지 않은 채 이전 release 파일/명령행 SHA를 결과에 붙인다. `probe_ai`도 release의 `deploymentUrl` 대신 `https://grand-site-dc.vercel.app`을 사용한다.

최소 재현 `probe-alias-moved-after-release`: 09:01에 A를 확인한 정상 release를 놓고, 09:04의 별칭 요청은 mock의 B가 처리하게 했다. 올바른 합성 계산 문장에 HTTP200을 반환했다. 결과는 `deploymentId=dpl_SYNTHETIC_RELEASE_A`, `streamOutcome=nonempty-finished`다. 요청 기록은 B가 처리했음을 보여준다. 내용이 맞더라도 A에서 관측했다는 출처는 틀릴 수 있다. 서버 함수만 다른 배포는 프런트 정적 바이트 비교만으로 구별되지 않을 수 있다.

최소 수정: 검증한 고정 deployment URL로 기능 요청을 묶고 공개 별칭의 접근성은 별도 확인하거나, 공개 별칭을 써야 하면 각 관측 묶음 직전·직후 같은 ID/URL임을 재확인하고 달라지면 해당 관측의 배포 귀속을 미확인으로 남긴다. 명령행 SHA만으로 귀속하지 않는다. 후자의 관측 사이 재배포 한계도 기록한다. 전부 위조된 파일을 판별하는 인증 기능이나 새로운 제품 기능은 요구하지 않는다.

## F02 — 시각이 하한만 통과하면 최신 관측으로 수락된다 (P2)

위치: `accept_basic_checks.py:14-24`, 모든 수집기의 처음 실행 시각 검사, `probe_ai.py:14,21`.

수락기는 관측과 release 시각이 09:00 이후인지만 확인한다. 현재 시각보다 미래인지, 관측이 release 확인보다 뒤인지, 10시 마감 전인지는 확인하지 않는다. 응답의 `fetchedAt`는 파싱 가능하기만 하면 된다.

| 고정 반례 | 실제 v4 판정 |
|---|---|
| 검증 시계 09:04, 관측 09:59 | 기본 검증 수락 |
| 관측 09:03, release 확인 09:03:30 | 기본 검증 수락 |
| 수집 10:01, 수락 10:02 | 기본 요청 8개 mock 실행 후 수락 |
| 용도지역 fetchedAt=2020-01-01 | 기본 검증 수락 |
| 용도지역 fetchedAt=2030-01-01 | 기본 검증 수락 |
| 짧은 AI 시작 10:01 | mock 추론 요청 1개 실행 후 텍스트 기록 |

오래된/미래 자료를 정상 최신 내용으로 세거나, 사용자 마감 이후 새 작업을 시작할 수 있는 도구상의 빈틈이다. 이번에는 모두 가짜 시계였으며 실제 마감 위반·네트워크 호출은 없었다.

최소 수정: 모든 신규 요청 전에 `09:00 <= now < 10:00`을 검사하고, 증거에는 timezone이 있는 시각과 `release <= observed <= now + 작은 허용 오차`를 적용한다. 긴 반복 수집은 각 요청 전에도 마감을 확인하고 완료/중단 상태를 구분한다. `fetchedAt`의 미래값은 거절하고 나이는 현재 제품의 freshness/캐시 계약에 맞춰 명시적으로 분류한다. API는 geocode max-age 3600, zoning/restrictions/disaster s-maxage 3600, nearby s-maxage 1800을 사용하므로 **fetchedAt가 무조건 09시 이후여야 한다는 새 규칙을 만들지 않는다.** 캐시 적중의 유효 범위와 자료 신선도를 구분하면 된다. 제품 `lookupContract.ts:31-34`는 이미 60초 초과 미래 메타데이터를 거절한다.

마감은 총괄의 명시적 운영 지침으로도 통제된다. 현재 스크립트가 시스템 차원의 정각 종료를 보장한다고 해석하지 않는다.

## F03 — complete 표기와 비어 있지 않은 queried만으로 본문을 수락한다 (P2)

위치: `accept_basic_checks.py:29-32`.

최소 반례는 서로 독립적이다.

- 규제 응답의 `queried`를 여섯 항목에서 `['LT_C_UD801']` 하나로 줄이고 `complete=true, failed=[]`를 유지해도 통과했다. 필요한 조회 집합을 다 수행했다는 증거가 아니다.
- 재해 응답에서 `found`를 빼도 통과했다. 명시적인 `found=false`와 필드 누락이 구별되지 않는다.
- 재해 응답을 `hits=[null]`로 바꿔도 통과했다. hits의 목록 여부만 검사하여 실제 항목 형식과 `found` 일치를 검증하지 않는다.

통제 사례에서는 정상 `found=false, hits=[]`가 통과하고 `complete=false`는 거절됐다. 정상적인 0건과 명시적인 false는 보존해야 하며 결측을 그 값으로 바꾸면 안 된다. `complete=true`도 “안전/인허가 가능”을 의미하지 않는다.

최소 수정: 제품에 이미 있는 `lookupContract.ts:46-51`의 조회 집합·중복·failed/complete 일치와 `disaster.ts:10-16`의 found/항목 계약을 오전 수락에도 적용한다. 규제·용도지역 항목 역시 해당 제품 파서와 맞춘다. 실제 제품 파서는 위 형태를 거절하도록 작성되어 있으므로 이 결과는 현재 제품 장애를 입증하지 않는다. 오전 수락기가 클라이언트가 거부할 본문을 “기본 API 성공”으로 셀 수 있다는 검증 누락이다.

## F04 — 주변 후보 ID·숫자·도형 계약이 클라이언트보다 약하다 (P2)

위치: `accept_basic_checks.py:33-39`.

첫 후보의 아래 값 하나만 바꾸고 실제 수집기 경로로 기록해도 모두 `nearby-sites-candidate-contract=true`, 전체 수락이었다.

| 변경 | 누락된 검증 |
|---|---|
| `distanceKm=true` | Python bool이 int 하위형이라 숫자처럼 허용됨 |
| `rings=[[]]` | 바깥 목록이 비어 있지 않은지만 검사함 |
| 첫 후보의 `id` 삭제 | 나머지와 중복되지 않은 None이 고유 ID처럼 계산됨 |

최소 수정: bool을 제외한 유한 실수인지 확인하고, ID는 비어 있지 않은 문자열인지 먼저 검사한 뒤 고유성을 비교한다. ring은 각 점의 수치·범위와 최소 길이·닫힘을 검사한다. 가능한 한 제품 `nearbySites.ts:17-25`의 기존 계약을 활용하여 단위 변환·중심점·최대 후보수 등도 같은 기준으로 대조한다. 점검 도구를 위해 새 제품 규칙이나 별도의 지리 알고리즘을 도입할 필요는 없다.

## 결함으로 보지 않은 경계와 오전 실행 주의점

1. **짧은 AI 문자열은 품질 성공이 아니다.** `probe-nonempty-is-not-quality`는 “60억원” 뒤에 전력·인허가 확정이라는 잘못된 문장을 반환했다. `nonempty-finished/expectedFinanceMention=true`이지만 `reviewedSemanticSuccess=null`, `full18ItemSuccess=null`을 유지했다. README는 한국어 계산과 미확인 문장을 직접 읽도록 요구한다. 그 수동 검수를 생략하지 않는 한 자동 품질 성공 오분류 결함으로 보고하지 않는다. 18항목/UI/부록은 여전히 별도 검수다.
2. `correlate_probe`는 ID 완전일치 불리언을 별도 남기고 강한 판정 문구도 “해당 배포·경로·시간창의 단일 이벤트”로 한정한다. 고유 요청 ID로 확정 연계했다고 주장하지 않는다. 그 명시된 한계를 결함으로 확장하지 않는다.
3. 전송 예외로 `probe_ai`가 `observation-failure.json`만 쓰면 `correlate_probe`가 요구하는 `short-probe/results.json`은 없다. 그때 진단 도구를 무조건 실행하면 FileNotFoundError다. 실패 파일/attempt를 보존하고 진단 미확인으로 보고하며, 짧은 요청을 재시도하지 않는다. 이는 README의 “오류 때 진단”을 HTTP 본문이 확보된 오류와 전송 실패로 구분할 운영 사항이다.
4. `verify_release`는 Git 연동의 정확한 final SHA 성공 배포만 통과시키도록 의도됐다. 현재 별칭이 Actions 배포이거나 Git 배포가 아직 준비되지 않았을 때 실패하는 것은 오수락이 아니다. 실제 계보를 추가 검수해야 한다.
5. `static.py`의 `localBuildHead`는 현재 git HEAD 관측일 뿐 기존 dist를 그 HEAD에서 빌드했다는 독립 증거는 아니다. 오전에는 검수한 제품 SHA와 frontend/dist 근거가 이어지는지 기록한다. 문서만 다른 HEAD라면 제품 범위 동일성 근거를 사용한다. 고정 34개 수는 의도된 현재 산출물 계약이며 새 파일이 추가되면 원인을 읽고 기준을 갱신해야 한다.
6. 각 결과 폴더/파일은 독점 생성 방식이다. 실패 후 원래 경로를 지우고 재실행해 성공으로 덮지 않는다. 네트워크 실패·관측 미완료를 보존하고 필요한 후속 관측이 승인·시간 범위 안에서 가능한지 총괄이 판단한다.
7. 브라우저 주요 스크린샷 직접 검토, AI 의미 직접 검토, actual alias 확인은 계속 필요하다. JSON의 pass 선언이나 모든 파일을 함께 교체한 위조를 탐지하는 인증 기능은 이 도구의 약속 범위가 아니므로 별도 결함으로 세지 않았다.

## 인계

N19는 위 네 군의 재현과 최소 수정 방향을 총괄에 인계한다. N06·제품의 수리는 하지 않았다. 전체 아침 관측을 실행하거나 완료로 표시하지 않았다. 총괄이 별도 수정·수락 검수를 거친 뒤 09시 작업에 적용해야 한다. 감사 종료 시 N19 자체 근거와 이 보고서를 root-relative bytes/SHA-256 manifest로 봉인하고 편집을 중지한다.
