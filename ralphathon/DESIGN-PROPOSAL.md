# 제품 흐름·디자인 제안 — 별도 반론 검수 전

작성일: 2026-09-21. 역할: 기획·디자인 제안 에이전트. 상태: **제안이며 최종 확정이 아님**. 별도 검수 에이전트의 반론과 총괄 결론을 `DECISIONS.md`에 남긴 뒤 구현한다.

이 문서는 `AGENTS.md`, `GOAL.md`, `STATUS.md`, `RESEARCH.md`, `BASELINE-AUDIT.md`와 실제 `App`, `ResultOverview`, `BusinessInputs`, `CompareDialog`, `MemoPanel`, `ChecklistReport`, `types`, `scoring/engine`, `report/checklist`, `index.css`를 읽고 작성했다. 외부 사이트 관찰은 총괄이 실제 분석 페이지·preview를 열람한 `RESEARCH.md`를 인계받은 것이다. 이 에이전트는 외부 사이트를 다시 열람하거나 코드·라이브 브라우저를 변경하지 않았다.

## 1. 제품을 관통하는 결정

**주소로 시작하고, 근거를 확인하고, 다음 조사할 후보를 비교 보고서로 정리한다.**

- 첫 사용에 필요한 것은 위치 하나다. 상세 사업정보·AI·가입을 검토 시작 조건으로 만들지 않는다.
- 첫 결과의 주제는 점수가 아니라 `확인된 제약 / 미확인 조건 / 다음 확인사항`이다.
- `공개자료 확인`, `사용자 입력`, `계산 가정`을 가까이 표시한다. 자료 확인을 전력 공급 가능·인허가 승인으로 표현하지 않는다.
- 비교와 보고서는 같은 현재 엔진 결과를 본다. 입력 변경 후 별도 저장·재분석 버튼을 눌러야 맞아지는 이중 상태를 만들지 않는다.
- 상세조건은 선택적으로 펼치되, 실제 전력·용수·통신 공급조건의 미확인은 기본 결과에도 남긴다. 미입력 폼을 숨기는 것과 검토 한계를 숨기는 것을 구분한다.
- 이 제품에서 `검토`는 공개자료와 입력조건에 따른 스크리닝이다. 서비스명 아래 짧은 설명과 보고서에 “스크리닝 참고용, 한전 공식 검토·법률 판단 대체 불가”를 유지한다.

### 권장안 B에 대한 반론과 응답

1. **“Cal.com과 IBM을 섞으면 일관성이 없는 것 아닌가?”**
   - 서로 다른 디자인 시스템을 설치하거나 화면별 토큰을 쓰지 않는다. 한 색상표·한글 글꼴·버튼·입력·상태 배지·구분선을 공유한다. 달라지는 것은 밀도뿐이다. 메인은 설명에 필요한 여백, 검토는 자료를 읽기 위한 행 구조다. A의 정렬, C의 근거 위계는 기능 원칙으로만 차용한다.
2. **“실무자는 곧장 지도를 보고 싶다. 메인이 한 번 더 클릭하게 만든다.”**
   - 독립 URL `/#review`를 제공한다. 공개 데모 첫 진입은 제품을 설명하되, 숙련자는 해당 URL로 바로 검토에 진입한다. 메인 `검토 시작`은 한 번만 필요하다. 첫 화면에서 별도 소개 확인·약관 동의·온보딩 완료를 요구하지 않는다.
3. **“상세를 접으면 무엇이 빠졌는지 알기 어렵다.”**
   - 기본 결과에 실제 공급조건 미확인과 핵심 공개자료 결측을 표시한다. 상세 입력 앞에는 `면적·비용은 조건을 입력하면 추가 검토합니다`를 둔다. 접힌 상세에는 `선택 · 미입력` 또는 `입력 있음 · 재검토 필요` 등 현재 상태를 텍스트로 표시한다. 오류가 생긴 폼은 접힌 채 숨기지 않는다.
4. **“지도를 줄이면 입지 서비스의 설득력이 약해진다.”**
   - 1440px에서 지도와 결과를 함께 보존한다. 390/768px에서는 지도·결과를 세로로 연결하고 결과 바로가기를 준다. 지도를 배경 장식으로 쓰지 않고 선택 위치, 공공 레이어, 주변 시설을 확인하는 도구로 유지한다.
5. **“짧은 요약은 과도하게 단순화할 수 있다.”**
   - 요약마다 `근거 보기`로 같은 화면의 해당 항목에 도달한다. 제약 0개나 녹색 배지를 `적합`으로 바꾸지 않는다. 보고서에 전체 18항목·출처·기준일·공간 단위를 보존한다.

### Paces/Felt에서 취하고 버리는 것

- [Paces](https://www.paces.com/): 초기 제약 확인과 후속 조사로 연결하는 검토 흐름을 취한다. 해외의 절감 수치·공급 보장·추가 데이터 범위를 우리 서비스의 사실처럼 쓰지 않는다.
- [Felt](https://felt.com/product): 지도에서 선택한 위치와 옆 자료가 같은 대상을 가리키는 연결, 보고서 내보내기를 취한다. 협업·로그인·클라우드 연결·지도 편집기 전체를 새로 만들지 않는다.
- 공개 프로젝트 및 라이선스는 `RESEARCH.md`의 Leaflet BSD-2-Clause, kepler.gl MIT 조사 기록을 따른다. 현재 Leaflet과 attribution을 유지한다. 이번 제안은 새로운 코드·폰트·디자인 자산 편입을 필요로 하지 않는다.

## 3. 화면 경로와 상태 수명

| 경로/상태 | 목적 | 진입/다음 행동 | 보존할 상태 |
|---|---|---|---|
| `/` 또는 `/#home` | 메인·제품 소개 | `주소로 검토 시작` → `/#review`; 페이지 내 `사용 방법`, `검토 범위` | 처음에는 대용량 자료·지도 코드 로딩 없음 |
| `/#review`, 위치 없음 | 주소 검색·지도 선택 | 주소/읍면동/좌표/지도 클릭 → 기본 결과 | 기존 검색 방식, 기본 project, 빈 conditions |
| `/#review`, 위치 선택 | 기본 검토 | 제약·미확인·다음 행동 → 상세조건/비교 담기/보고서 보기 | 현재 위치, 온라인 조회 상태·결과, 공통·개별 입력 |
| 같은 경로, 상세 펼침 | 선택 상세조건 | 변경 즉시 현재 결과·담긴 후보 갱신 | 공통조건과 부지별 조건의 경계 유지 |
| 같은 경로, 비교 dialog | 최대 4곳 같은 기준 비교 | 후보 제거, 조건·지도 열기, 해당 후보 보고서 열기 | `pins.ts`의 후보 식별·스냅샷·재계산 |
| 같은 경로, 보고서 dialog 또는 보고서 전용 펼침 영역 | 기본 보고서 읽기·A4 PDF | `PDF 저장`, 닫고 결과 복귀, 선택 AI 의견 | 현재 input/result/checklist, AI 유효성 |

새 라우터는 추가하지 않는다. 작은 hash 전환으로 독립 메인/검토 URL을 제공해 새로고침·앞으로/뒤로·Lighthouse 측정이 가능하게 한다. 해시를 사업조건 직렬화·외부 공유 저장으로 사용하지 않는다. `/review` 같은 하위 실제 경로를 새로 만들지 않으면 기존 `base:'./'`, 상대 자료 경로의 회귀 위험이 작다.

메인으로 돌아갔다 검토에 재진입해도 현재 후보·조건이 사라지지 않아야 한다. 권장 구현은 최초 검토 진입 후 workspace를 유지하고 홈에서는 `hidden`으로 감추는 방식이다. 최초 메인 진입에는 workspace를 mount하지 않는다. 재표시할 때 Leaflet 크기 재계산을 확인하고 감춘 트리의 초점·PrintPortal이 남지 않게 한다. 단순 조건부 unmount로 상태를 잃는 구현은 금지한다. 더 단순한 명시적 상위 상태 유지도 가능하나 계산·조회 상태를 이중 저장하지 않는다. 후보는 현 브라우저 세션 내 상태이며 새로고침 뒤 보존을 약속하지 않는다.

보고서를 별도 dialog로 만들면 비교 dialog를 먼저 닫고 선택 후보를 열어 그 후보의 보고서를 표시한다. 모달을 중첩하지 않는다. 개발량을 줄이려면 한 보고서 영역을 열고 제목으로 이동하는 방식도 허용하되, 상세 근거 끝까지 스크롤해야만 보고서에 도달하는 구조는 피한다.

## 4. 메인 — 제품을 이해하고 바로 시작

### 첫 화면

- 상단: `여기 DC 돼요?` / 제품 소개 / 검토 시작. 비공식 GS 로고를 새로 만들거나 승인·공식 운영을 암시하는 표장을 사용하지 않는다.
- 작은 문구: `데이터센터 후보 부지 1차 검토`.
- 제목: `주소에서 시작해, 다음 확인사항까지.`
- 설명: `전력·인허가·재해·주변 현황을 같은 기준으로 살펴보고, 확인된 제약과 미확인 조건을 보고서로 정리합니다.`
- 주 행동: `주소로 검토 시작`.
- 보조 안내: `내부 사업정보 없이 시작 · AI 없이 기본 보고서 사용`.
- 오른쪽 또는 아래: 정적인 자체 HTML 보고서 예시. `화면 구성 예시`를 명시하고 `전력 공급조건 — 미확인`, `공개자료 — 출처와 기준일 표시`, `다음 확인 — 공급기관 협의`처럼 기능을 보여준다. 가짜 주소의 실제 위험도·실적·절감 숫자를 만들지 않는다. 실시간 지도를 여기에 넣지 않는다.

### 아래 세 묶음

1. `주소 선택 → 기본 검토 → 후보 비교·보고서`의 세 단계. 선택 상세조건은 기본 검토 설명 안에 보조 단계로 둔다.
2. 확인 범위: 전력 / 인허가·재해 / 주변 현황 / 선택 면적·비용. 각 1문장과 자료 한계. “전력 공급량 확인”, “허가 가능 판정”이라고 쓰지 않는다.
3. 활용: `GS건설의 후보 부지 검토를 위한 도구입니다. 같은 형식의 보고서는 그룹 내 관련 조직과 검토 근거를 공유하는 데 활용할 수 있습니다.` 실제 협업 기능이 있는 것처럼 쓰지 않는다.

마지막에 짧은 출처·범위 안내와 검토 시작을 반복한다. 측정하지 않은 소요시간·절감률·“원클릭 승인” 등의 문구는 없다.

## 5. 검토 workspace — 순서와 내용

### 5.1 위치 선택

- 지도 위에 검색 UI를 복잡하게 겹치지 않고 검색은 지도 상단의 독립 행으로 둔다. 입력 라벨은 `후보지 주소 또는 읍면동`; 좌표 입력 가능 여부를 도움말로 제공한다.
- 빈 입력: `주소나 읍면동을 입력해 주세요.`를 해당 입력 아래 알림. 미발견: 입력을 유지하고 `검색 결과를 찾지 못했습니다. 읍면동 또는 좌표로 다시 검색하거나 지도에서 선택하세요.` 표시.
- 온라인 주소 조회 실패: 현재 선택/결과는 유지하고 오류 안내와 재시도·지도/읍면동 대안을 제공한다. 실패를 `주소가 없음`으로 바꾸지 않는다.
- 실제 선택 주소, 선택 방식, 좌표를 결과 제목 가까이에 표시한다. 읍면동 중심점을 필지 주소처럼 표현하지 않는다.
- 검색 응답이 늦게 도착해도 최신 지도/목록/좌표 선택을 덮지 않는다. 요청 세대 또는 abort와 선택 의도를 함께 관리한다.
- 지도를 쓰기 어려운 사용자도 주소·좌표로 동일 결과에 도달한다. 키보드 초점을 지도에서 결과로 건너뛸 링크를 제공한다.

### 5.2 결과 상단의 고정 위계

1. 위치와 `공개자료 조회 중 / 현재 입력 기준 / 일부 자료 미확인` 상태.
2. 엔진의 현 검토 상태와 짧은 이유. 법적 입지 제한은 다른 조회가 실패해도 계속 표시한다.
3. **확인된 제약**: 실제 관측된 제한·검토 대상. 근거 성격을 함께 표시.
4. **미확인 조건**: 핵심 자료 결측·부분 조회, 전력·용수·통신 공급조건. 상세 입력이 전혀 없으면 면적·비용은 한 줄 `상세조건을 입력하면 면적·비용을 추가 검토합니다`로 안내한다.
5. **다음 확인사항**: 해당 제약/미확인에서 이어지는 우선 행동. 최대 3개를 먼저 보이고 나머지 전체 목록으로 연결한다.
6. `보고서 보기`와 `비교에 담기`를 결과 상단에서 발견할 수 있게 한다.
7. `상세조건 추가 · 선택`, `근거와 주변 현황`, `참고점수와 산정 근거`를 차례로 둔다.

첫 세 묶음은 지나치게 큰 카드 세 개 대신 제목·작은 상태 배지·2~3행의 요약을 가진 수직 구획으로 구성한다. 1440px에서도 패널 안 세 열로 압축하지 않는다. 장문 전체 근거는 해당 항목을 펼쳐 확인한다.

### 5.3 제약·미확인을 잘못 분류하지 않기 위한 데이터 경계

현재 `ReviewIssue`에는 title/detail/tone만 있다. **tone=risk를 무조건 “확인된 제약”으로 분류하거나 문구에 “미확인”이 포함되는지로 구분하면 안 된다.** 실제로 사용자 선택 용도지역에 따른 `조례상 입지 제한 검토`도 risk이며, 자료에 따른 확정된 제한과 같은 의미가 아니다.

권장 구현은 `scoreSite()`가 기존 판단을 이용해 요약용 의미를 추가로 반환하는 것이다. 예를 들어 stable key, `확인사항/미확인/입력조건`, `공개자료/사용자입력/계산`, 연관 다음 행동을 반환하고 UI·비교·보고서는 같은 결과를 표시한다. `report/`의 순수 포맷 함수는 행 조합·표현만 담당한다. UI에 제한 판정·금융비용·면적 산식·새 점수·임계값을 복제하지 않는다. 필드 추가 범위는 개발 에이전트가 최소화하되 엔진의 골든·규제·재해·보고서 회귀로 검증한다.

| 엔진 상태의 예 | 보여줄 위치와 표현 | 피할 표현 |
|---|---|---|
| 공개자료 법적 입지 제한 해당 | 확인된 제약에 `법적 입지 제한 구역 · 공개자료`; 근거 도면·최신 고시 확인 행동 | 단순 “개발 불가 확정” |
| 재해위험지구 hit | 확인된 제약에 `재해위험지구 해당 · 관할기관 검토 필요`; 해당 사실과 영향 판단 구별 | “위험 부지 탈락” |
| 사용자 용도지역에 따른 조례 검토 | `사용자 입력에 따른 검토사항`; 공식 용도지역·적용 조례 확인 전 확정 배지 금지 | “확인된 법적 금지” |
| 입력 면적 부족 | `입력조건상 최소 대지 부족 · 계산 가정`; 대표 산식의 단순 가정 표시 | 실측 불가능·인허가 불가 |
| 규제/재해 조회 실패·일부 실패 | 미확인 조건에 해당 조회 상태, 재확인 행동 | 규제 없음·안전 |
| 공개 변전소 목록 있음 | 근거 상세에 등재 사실, 공급조건은 별도 미확인 | 공급 용량 확보 |
| 현재 확인된 제약 없음 | `현재 확인된 자료에서 제약 항목이 없습니다. 미확인 조건은 별도 확인하세요.` | 적합·안전·통과 |

### 5.4 선택 상세조건

- 상세 전체의 입구를 하나로 하고 내부는 `공통 사업조건`, `이 부지의 면적`, `이 부지의 비용·공급 협의`로 구분한다. 기존 필드를 삭제하지 않는다.
- 공통조건에 `담은 모든 후보에 적용`을 표시한다. 개별조건에는 현재 후보 이름을 표시한다. 연면적·용적률·건폐율·층수 등 실제 필드의 공통/개별 배치는 기존 타입을 따른다. 겉보기 그룹명을 이유로 상태 소속을 바꾸지 않는다.
- 유형은 실제 고정 MW가 아님을 유지한다. 현재 큰 규모 선택 카드도 상세 안으로 옮겨 주소만으로 시작하는 흐름을 방해하지 않게 한다.
- 숫자 입력에는 영구 라벨·단위·미입력 상태를 둔다. 빈 값은 `null`, 0은 `0` 그대로 표현한다. 필수 양수 항목의 0/음수·소수 층수·초과 비율은 해당 입력 아래 오류와 계산 보류 이유로 보인다.
- 잘못된 값을 조용히 다른 값으로 보정하거나, `|| 0` 같은 방식으로 결측을 비용 0으로 만들지 않는다.
- 계산 결과는 입력 가까이에 짧게 보여준다. 예: `입력조건상 최소 대지 15,000㎡`, `지연 12개월 가정 금융비용 60억원`. 결과만 재계산하며 전체 페이지 초점을 이동시키지 않는다.
- 입력 변경 시 `현재 입력을 결과와 보고서에 반영했습니다` 정도의 정중한 live 안내를 배치하되 매 키 입력마다 긴 결과를 읽게 하지 않는다.

### 5.5 지도와 기존 부가 기능

- 기존 타일·공개 DC 목록·사례·규제 레이어·상세 위치 이동을 유지한다. 레이어 제어는 기본 접힘으로 검색·주소 결과를 덮지 않는다.
- 인근 필지 탐색은 `면적 기준 인근 후보 탐색 · 선택`의 명시적 실행으로 둔다. 단순 좌표 선택마다 대량 조회하지 않는다. 부분 범위·도형 추정 면적·권리/접도 미확인 표시를 보존한다.
- 주변 인구·가구·학교·참고 기사·허가 통계는 `근거와 주변 현황`에서 출처·시점과 함께 제공한다. 수용성 등급·인구가 적으면 민원 가능성이 낮다는 새 판단은 없다.
- 참고점수는 보조 상세에 숫자와 산정 이유를 보존한다. 미산정은 대시만 쓰지 않고 사유를 함께 표시한다. 높은 점수에 거대한 녹색 배지나 “추천” 표시를 붙이지 않는다.

## 6. 비교 — 목록 관리와 다음 행동

- 전역 접근은 `후보 비교 2/4`처럼 현재 수를 표시한다. 현재 후보 담기 버튼은 항상 같은 위치·같은 의미를 갖는다. 첫 후보 담은 뒤 같은 버튼이 갑자기 비교 열기로 바뀌지 않게 한다.
- 4곳 상태: 기존 후보는 그대로 보존하고 `최대 4곳까지 비교할 수 있습니다. 후보를 하나 제거하면 새 후보를 담을 수 있습니다.` 표시. 5번째 자동 교체 금지.
- 현재 후보가 이미 담겼으면 `담긴 후보` 상태. 제거는 후보 이름을 포함한 접근 가능한 버튼으로 제공하고 목록 변화와 초점 이동을 안내한다.
- 비교표 순서: 위치/현재 조건 → 확인된 제약 → 미확인 조건 → 다음 확인사항 → 면적/비용 → 전력·규제·재해·주변 근거 → 참고점수. 과도한 세로 길이를 막으려면 후반 상세 행을 접을 수 있으나 모든 데이터에 도달 가능해야 한다.
- 비용 완전성·방식·범위가 같을 때만 차액을 표시한다. 결측을 최저비용·0억원·순위로 바꾸지 않는다. 자동 최적 후보 선정은 없다.
- 후보별 동작은 `조건·지도 보기`, `이 후보 보고서`, `후보에서 제거`. 보고서 열기는 선택 후보의 저장 조건을 복원하고 최신 공통조건/자료를 반영한 결과를 쓴다.
- 1곳이어도 목록 관리·보고서는 가능하며 비교에는 2곳 이상 필요하다는 안내만 한다. 빈 비교창은 주소 선택으로 돌아가는 행동을 제공한다.
- 4후보 일괄 PDF는 이번 필수 범위에 추가하지 않는다. 각 후보의 보고서를 제대로 연결하고 비교표에서 후속 조사 후보를 고르는 흐름을 완성한다.

## 7. 보고서·A4 PDF·AI의 분리

### 기본 보고서

첫 장은 `위치·작성 기준 → 확인된 제약 → 미확인 조건 → 우선 다음 행동 → 입력한 경우 면적·비용 요약 → 짧은 한계`다. 상세 미입력 보고서의 첫 장을 “미입력” 숫자 표로 채우지 않는다. 뒤쪽에는 현재 입력 전체, 공급 협의 기록, 18개 체크리스트, 출처·기준일·공간 단위·자료 한계를 유지한다.

현재 `r.review.actions.slice(-2)`만 보여주는 첫 장을 교체한다. 실제 규제·재해·공급 미확인과 연결된 우선 행동을 먼저 표시하고, 일반 설계·인입 안내는 뒤의 전체 목록에 남긴다. 표현이나 순서를 정하는 기준도 엔진/공통 보고서 모델 한곳에서 관리한다.

- `보고서 보기`는 AI 생성 전부터 활성이다. `PDF 저장`이 보고서의 주 버튼이다.
- A4 portrait, 15mm/14mm 기존 여백을 출발점으로 삼는다. 인쇄는 기존 `PrintPortal`과 제목 설정을 재사용한다.
- 화면은 좁은 폭에 맞춰 문서 내용을 흐르게 한다. 모바일에서 A4 전체를 작게 축소한 이미지처럼 보여주지 않는다.
- 첫 장에 고정 픽셀 높이를 강제해 긴 주소·제약 문장이 잘리지 않게 한다. 상세표 행은 페이지 반복 머리글·줄바꿈·행 분할을 실제 PDF로 확인한다. 출처 URL은 길면 줄바꿈한다.
- 목표의 “최대 5페이지”는 발표자료 조건이지 보고서 제한이 아니다. 보고서 페이지 수를 인위적으로 줄여 근거를 버리지 않는다.
- 입력/조회 근거 변경은 열린 보고서와 print 트리에 즉시 반영된다. 화면용/인쇄용 JSX를 별도 판정 코드로 만들지 않는다.

### 선택 AI

`AI 의견 추가 · 선택`은 PDF 버튼 아래 별도 접힘 영역이다. 기본 보고서와 AI 버튼이 동등한 선행 단계로 보이지 않게 한다. 현재 `MemoPanel`에서 기본 보고서 표시·인쇄와 AI 생성 책임을 분리하되 체크리스트·input/result를 복제 저장하지 않는다.

- 생성 전: 기본 보고서 사용 가능 안내.
- 생성 중: 중지 가능; 기본 보고서·비교·입력은 계속 가능.
- 실패: `AI 의견을 불러오지 못했습니다. 기본 보고서와 PDF는 계속 사용할 수 있습니다.`와 재시도. 원문 업스트림 오류는 보여주지 않는다.
- 입력/근거 변경: 즉시 이전 AI 의견 해제·진행 요청 중단. `조건이 바뀌어 이전 AI 의견을 해제했습니다. 기본 보고서는 갱신되었습니다.` 표시.
- 조건을 이전 값으로 되돌려도 중단·무효 의견을 재사용하지 않는다. v4 서명과 invalidated 규칙을 유지한다.
- 보고서에 AI를 넣는 경우 생성 당시 조건과 일치하는 의견만 별도 제목 아래 표시한다. 완료 전 부분 생성은 상태를 명시한다. 기본 근거와 AI 문장을 혼합해 확정 사실처럼 보이지 않게 한다.

## 8. 화면 크기·키보드·색상·한글

### 크기별 구성

| 검증 폭 | 구성 | 특별 확인 |
|---|---|---|
| 1440px | 메인 콘텐츠 최대 약 1120~1200px. workspace 지도+결과 2열, 기존 패널 너비 조절 유지. 검색은 지도 위 독립 행. 결과 패널은 최소 약 460px의 읽을 폭 확보 | 지도 확대/레이어/검색이 겹치지 않음. 패널 리사이저 키보드·축소 한계. 긴 주소 2~3줄 허용 |
| 768px | workspace 세로 구성. 검색→약 320px 지도→결과. 결과/지도 바로가기. 결과는 화면 전체 폭 | 데스크톱 2열을 억지 유지해 300px 패널을 만들지 않음. 지도 때문에 결과 접근이 지나치게 멀어지지 않음 |
| 390px | 검색/버튼은 필요시 두 줄. 지도 약 240~280px, 결과는 16px 좌우 여백. 현재 후보 담기·보고서 동작은 세로 또는 2열로 정리 | 고정 하단바가 오류/출처/모바일 키보드를 가리지 않음. 메뉴·긴 숫자·좌표·단위·표의 문서 전체 가로 넘침 없음 |

모바일 비교표만 독립된 가로 스크롤을 허용한다. 첫 항목 열·후보 이름을 읽을 수 있게 하고 `좌우로 이동하여 최대 4곳을 비교하세요`를 표시한다. 스크롤 영역에 이름과 키보드 접근성을 제공한다. 나머지 문서 전체에는 가로 스크롤이 없어야 한다. 작은 화면에서 별도 차트나 완전히 다른 비교 상태를 만들지 않는다.

모바일은 전체 문서 하나의 세로 스크롤을 기본으로 한다. 지도 안 스크롤·패널 안 스크롤·페이지 스크롤 3개가 겹치는 것을 피한다. 중요한 결과를 펼치고 나면 검색으로 다시 돌아갈 수 있다. 데스크톱 지도/결과 독립 스크롤은 기존 장점을 유지한다.

### 키보드·보조기술

- 메인 콘텐츠/검색/결과로 건너뛰는 링크; 페이지별 하나의 주 제목.
- combobox는 실제 label, `aria-expanded`, `aria-controls`, `aria-activedescendant`, 안정된 option id를 연결. 방향키/Enter/Escape를 실제 시험한다.
- 선택 후 결과 요약을 짧게 알려주되 지도에서 클릭할 때마다 초점을 강제로 빼앗지 않는다. 키보드 검색 선택 시 결과 제목으로 이동하는 명확한 경로를 제공한다.
- native `details`, `button`, `fieldset/legend`, `dialog`를 활용한다. dialog는 이름, Escape 닫기, 초점 가두기, 열기 버튼으로 초점 복귀를 확인한다.
- 오류는 라벨에 연결된 안내와 `aria-invalid`, 한 번의 alert로 알린다. 로딩은 상태 텍스트와 `aria-busy`로 표현한다. 스켈레톤만 보이지 않는다.
- 터치 목표는 주요 입력·버튼 최소 44px를 목표로 하고 숫자/태그가 작아져도 클릭 영역은 유지한다.
- `prefers-reduced-motion`을 존중하고 자동 움직임·초기 영상·반짝이는 상태점은 쓰지 않는다.

### 토큰 제안과 계산한 대비

기존 `--brand: #d65f14`는 브랜드의 핵심색으로 보존한다. 작은 흰 글자가 들어가는 버튼은 같은 오렌지 계열의 더 진한 값을 쓴다. 아래 대비는 sRGB 상대 휘도 공식으로 이 에이전트가 계산한 **색상 쌍 자체의 수치**이며 실제 화면·axe 검증 통과를 뜻하지 않는다.

| 용도 | 전경 / 배경 | 계산 대비 | 적용 |
|---|---|---|---|
| 기존 브랜드 오렌지 | `#d65f14` / `#ffffff` | 3.81:1 | 장식선·넓은 심벌·강조. 작은 흰 본문 버튼에는 사용하지 않음 |
| 주요 오렌지 버튼 | `#ffffff` / `#b5470a` | 5.43:1 | 흰 글자 CTA |
| 링크/진한 오렌지 | `#973b08` / `#ffffff` | 7.13:1 | 작은 링크·선택 텍스트 |
| 본문 | `#202723` / `#ffffff` | 15.26:1 | 긴 근거·수치 |
| 보조 설명 | `#596159` / `#f7f7f3` | 5.96:1 | 라벨·출처. opacity로 다시 낮추지 않음 |
| 제약 상태 | `#9f342c` / `#fff3f1` | 6.44:1 | `제약 확인` 문구·아이콘 병기 |
| 추가 검토 | `#805b0a` / `#fff7e1` | 5.75:1 | `검토 필요` 문구 병기 |
| 미확인 | `#4b5b64` / `#edf2f5` | 6.25:1 | `미확인`, `일부 미확인` |
| 자료 확인 | `#235f55` / `#edf5f2` | 6.67:1 | `자료 확인`; 사업 적합·안전 의미로 쓰지 않음 |

밝은 표 경계선은 구조 보조로만 사용한다. 조작 가능한 입력 테두리·포커스 윤곽·아이콘은 실제 인접색 대비를 별도로 확인한다. 상태색은 글자·아이콘과 함께 쓰고 전체 지도를 초록/빨강으로 덮어 판정처럼 보이게 하지 않는다.

한글은 새 외부 웹폰트 요청 없이 기존 시스템 글꼴 기반으로 시작한다. `'Malgun Gothic', 'Apple SD Gothic Neo', 'Segoe UI', sans-serif` 계열을 사용하고 실제 Windows/브라우저 렌더로 확인한다. 메인 제목 약 40~48px(모바일 30~34px), 화면 제목 24~28px, 본문 15~16px/행간 1.6, 보조 글 13~14px를 출발점으로 삼는다. 핵심 근거·입력·버튼에 기존 8~10px 글씨를 쓰지 않는다. 표 숫자는 tabular-nums, 단위와 값은 의미상 한 덩어리로 읽게 한다. 과도한 음수 자간·얇은 한글 제목·영문 전용 대문자 eyebrow를 줄인다. 주소/출처는 필요한 줄바꿈이 가능해야 한다.

## 9. 코드와 디렉터리 경계 — 구현 인계

```text
prototype/src/
  App.tsx                       # 경량 화면 전환·공통 탐색·lazy boundary
  pages/
    HomePage.tsx                # 설명·검토 시작, 데이터/Leaflet 의존 없음
    ReviewWorkspace.tsx        # 현재 App의 상태·조회·계산 orchestration 계승
  components/
    ReviewSummary.tsx          # 엔진이 정한 요약을 표시
    ReportPanel.tsx            # 기본 보고서 도구/미리보기, 필요할 때 분리
    MemoPanel.tsx              # 선택 AI 생성·서명·무효화
    SiteSearch.tsx MapView.tsx BusinessInputs.tsx CompareDialog.tsx
    ChecklistReport.tsx PrintPortal.tsx ...
  scoring/                     # scoreSite 단일 판단·계산, 요약 의미의 원천
  compare/                     # 기존 pins 식별·제한·재계산
  report/                      # 체크리스트·공통 포맷, 새 판정 금지
  genai/                       # 서명·실행·파싱의 기존 경계
  hooks/                       # 데이터/조회 요청 수명주기
  styles/                      # home/workspace/print 필요시 점진 분리
```

- `ReviewWorkspace`를 `React.lazy`로 로드한다. 메인에서 지도·큰 JSON·AI 코드가 불필요하게 요청되지 않는지 production network로 확인한다. `index.css`의 전역 Leaflet import도 메인 분리를 방해하는지 확인하되 무조건 파일을 전부 재편하지 않는다.
- 공통 헤더/오류/로딩은 lazy chunk가 오기 전 표시 가능해야 한다. 검토 자료 로딩 중에도 무엇을 하는지·재시도 방법을 알 수 있게 한다.
- 핵심 자료 실패는 안전한 계산 보류와 재시도. 부가 사례·뉴스·DC 목록 실패는 해당 영역 미확인으로 격리한다. 규제 배열을 빈 배열로 대체해 “해당 없음”이라고 만들지 않는다.
- 기존 `ResultOverview`의 점수·분해·감점은 보조 상세로 보존하거나 작은 표시 컴포넌트로 분리한다. 새 `ReviewSummary`와 기존 `ResultOverview` 둘 다 큰 요약을 표시하게 하지 않는다.
- `ChecklistReport`와 `PrintPortal` 인스턴스는 현재 유효 보고서를 기준으로 하나의 경계를 공유한다. 새 ReportPanel 분리 때문에 `buildChecklist`·AI snapshot·보고서 state를 서로 달리 저장하지 않는다.
- 미사용 호환 re-export·CSS·Vite 자산은 import 확인 후 별도 작은 정리만 한다. 이동을 위한 이동, 의존성 추가, 새로운 상태관리·라우터·차트·UI 프레임워크는 하지 않는다.

## 10. 작은 구현 순서와 독립 검수 조건

| 순서 | 작은 작업 | 이 단계에서 확인할 내용 |
|---|---|---|
| 1 | 메인/검토 분리, lazy load, hash 경로 | cold 메인에 데이터/지도 요청 없음, 직접 검토 URL 새로고침, 홈 왕복 상태 유지, 키보드 시작 |
| 2 | 엔진의 요약 의미/표현 모델과 결과 위계 | 기존 대표 산식·점수·규제·재해 결과 불변, 사용자 입력을 공개 확인으로 오인하지 않음, 공급 미확인 항상 발견 가능 |
| 3 | 상세 입력 재배치·보고서/AI 동선 분리 | 주소만 결과/보고서, 잘못된 숫자/0/결측, 현재 결과와 보고서 일치, AI 없이 PDF |
| 4 | 비교 동선·공통/개별 변경·후보 보고서 | 추가 1→4, 5번째 제한, 제거 후 추가, 후보 열기와 조건 복원, 공통 변경 전체 갱신 |
| 5 | 검색 경쟁·부가 실패·AI 무효화·API 안전 처리 | 늦은 주소 응답·부가 JSON 실패·AI 실패가 가능한 기본 기능을 막지 않음. 진행/완료 AI 후 입력·근거 변경과 원상복귀 |
| 6 | 최종 화면·접근성·A4 조정 | 390/768/1440, Tab/Enter/Escape/초점 복귀, 기본·상세 PDF 전체 페이지, axe 핵심 화면 |
| 7 | 측정과 실제 배포 검증 | 메인/앱 동일 조건 Lighthouse 각 3회, 중앙값·원본 보고서. 품질 목표 미달을 수치로 기록 |

디자인 검수의 합격 조건은 예쁜 첫 화면만으로 충족되지 않는다. 아래 항목을 별도로 판단해야 한다.

1. 주소만 입력하고 상세/AI를 건드리지 않아도 보고서에 도달하는가.
2. 현재 확인된 제약과 미확인 공급조건을 구분하고 실제 자료 결측을 발견할 수 있는가.
3. 자료/조건 변경 시 요약·비교·보고서가 일치하고 이전 AI가 섞이지 않는가.
4. 모바일에서 검색·지도·첫 결과·다음 행동·보고서가 가려지지 않고 이어지는가.
5. 0/미입력, 계산 가정/확인 사실, 공개자료 목록/공급 가능량을 서로 구분하는가.
6. 기존 지도·상세설계·4후보·18항목·필지 탐색 기능이 삭제되지 않았는가.
7. 메인·앱의 측정 조건을 문서화할 수 있고, 기본 보고서의 전체 PDF가 읽히는가.

## 11. 별도 검수자에게 요청할 반론

- B안이 주안이라는 결정은 충분히 명료한가. 독립된 디자인 시스템 세 개를 혼합하는 것으로 읽히지 않는가.
- 메인 때문에 검토 진입이 길어지거나, 상세를 숨긴 결과 공급조건 미확인을 놓치지 않는가.
- 의미 메타데이터를 엔진에서 내보내는 변경이 단일 기준을 강화하는가. 더 작은 변경으로 동일한 오분류 방지를 달성할 대안이 있는가.
- `/#home ↔ /#review` 상태 유지·lazy loading·print portal이 충돌할 위험을 충분히 통제했는가.
- 보고서 동선 분리에서 기존 AI 무효화·중단·사전생성 서명 검증이 약화될 여지가 없는가.
- 모바일 비교표의 제한적 가로 스크롤이 적절한가. 별도 복제 상태 없이 더 나은 접근 방법이 있는가.

**권장 결론:** B안을 서비스 전체의 진입·행동 원칙으로 채택하고, 동일한 GS 오렌지 토큰과 한글 타이포 아래 업무 자료의 밀도만 조절한다. 첫 결과·비교·보고서의 공통 축은 확인된 제약, 미확인 조건, 다음 확인사항이다. 기존 엔진·데이터·지도·상세·보고서를 재사용하는 범위에서 목적에 가장 직접적이며, 메인 경량화와 검증 가능한 상태 경계를 함께 만들 수 있다. 이 결론의 확정과 변경 사유 기록은 총괄이 별도 반론 검수 후 수행한다.
