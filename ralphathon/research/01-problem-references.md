| 선택 상세 | 선택 후보 위치 → 주요 제약 → 중요한 미확인 → 다음 확인 → 상세근거 순서 | 큰 참고점수가 근거와 미확인보다 앞서 결론처럼 보이지 않음 |
| 검색과 후보 담기 | ‘현재 검토 중’과 ‘비교에 담은 후보’를 구별, 명시적 추가·제거 | 검색/지도 클릭만으로 기존 후보를 덮어쓰거나 4개 제한을 우회하지 않음 |
| 지도와 표 | 비교 목록에서 선택하면 해당 후보·입력 복원, 동일 식별자 사용 | 늦은 외부 응답이 다른 후보의 상태를 덮어쓰지 않음 |
| 작은 화면 | 390px에서는 지도와 상세를 명시적 전환하거나 충분한 높이의 지도 뒤에 상세 배치 | 지도 위 다중 패널로 전체 화면을 가리지 않음, 선택 상태 유지 |

**범위 제안:** Felt의 기능 목록 전체를 복제하지 않는다. 실시간 협업·공유 권한·광범위한 파일 업로드·3D·도형 편집은 사용자 Goal의 요구가 아니며 현재 추가하지 않는다. 기존 지도·검색·비교·보고서와 소개 페이지를 모두 완성하는 범위는 그대로다.

getdesign 미리보기의 예시 수치·가상 고객 발언·가격과 ‘아이콘이 시각적으로 가운데 있으면 작은 터치 타깃을 보완한다’는 식의 설명을 제품 근거나 접근성 기준으로 전용하지 않는다. 접근성은 실제 앱과 W3C 기준으로 검증한다.

## 6. 공개 유사 서비스의 흐름 비교

| 서비스 | 문서에서 확인한 흐름·구조 | 재사용할 원칙 | 이번 비적용·한계 |
|---|---|---|---|
| **Paces** | 자료/필터로 입지 탐색 → 중첩 제약 검토 → 프로젝트 진행관리 → 전문가 보고서·신청 지원. 위 3개 공식 페이지 | 주소·조건·근거·다음 행동의 연결, 결과가 후속 검토로 이어짐 | 미국 중심 자료·계통해석·전문가 확약·신청 대행을 한국 공개자료 앱의 기능처럼 표시하지 않음. 로그인 제품 미사용 |
| **Felt** | 자료 추가 → 레이어/범례/표 → 상세 선택 → 시각화·공유. 위 공식 도움말 | 지도와 목록의 같은 데이터, 선택 상세, 명확한 조작 도구, 검색과 추가의 구별 | 실시간 협업·권한·업로드·클라우드 연결 도입 없음. 제품 설명의 속도 주장 독립 검증 안 함 |
| **Glint Solar** | 프로젝트 중심 입지 탐색/기존 후보 평가 → 레이어·필터 → 설계/분석 → 지도와 범례의 내보내기 → 포트폴리오 지도/보드. [공식 시작 안내](https://knowledgebase.glintsolar.com/en/article/how-to-start-using-glint-solar) | 보고서에 지도의 의미·범례·근거를 함께 전달, 탐색한 위치와 저장한 프로젝트 구별 | 태양광·BESS 수익/발전량 모델·3D·협업은 별개 분야. 홍보된 개발시간 절감·성공률을 인용하지 않음 |

Glint는 기능 채택 후보를 늘리기 위한 조사 대상이 아니라, 입지 평가 결과가 어떻게 보고·협의로 넘어가는지 비교한 유사 서비스다. 세 서비스의 공통점에서 도출한 설계 제안은 ‘지도에서 보기 → 근거가 있는 상태로 정리 → 후속 행동’이며 이는 **조사자의 해석**이다.

## 7. GitHub 프로젝트: 구조·실제 문서 흐름·라이선스

2026-09-21 GitHub API로 저장소 메타데이터, 기본 브랜치, README, 루트 라이선스와 주요 디렉터리를 읽었다. 저장소 전체 clone·의존성 설치·코드 복사·제품 실행은 하지 않았다. 각 저장소의 당시 공개 상태는 보관한 `*-metadata.json`을 따른다.

| 프로젝트 | 확인한 구조·사용 흐름 | 라이선스 원문과 적용 판단 | 이번 차용 단위 |
|---|---|---|---|
| [Kepler.gl](https://github.com/keplergl/kepler.gl) | React/Redux, MapLibre/deck.gl. `src/actions`, `reducers`, `processors`, `schemas`, `components`, `layers`가 분리됨. 자료 → 레이어 → 필터 → 저장/내보내기. [사용 안내](https://docs.kepler.gl/docs/user-guides) · [내보내기](https://docs.kepler.gl/docs/user-guides/k-save-and-export) | [MIT](https://github.com/keplergl/kepler.gl/blob/master/LICENSE) 원문 확인. 코드 실질 복제 시 고지 보존 조건 검토 필요. 여기서는 코드를 가져오지 않음 | 데이터/표시 설정/화면의 역할 분리, 내보내기 전 상태 확인. 새 Redux·지도 엔진을 넣지 않음 |
| [TerriaJS](https://github.com/TerriaJS/terriajs) | 현재 `apps/`, `packages/` 모노레포; `packages/terriajs/lib` 안에 `Core`, `Map`, `Models`, `ReactViews`, `Traits` 등. 카탈로그/워크벤치 → 지도 데이터 → 상세정보 → 공유·인쇄. [사용 안내](https://userguide.terria.io/) · [MONOREPO](https://github.com/TerriaJS/terriajs/blob/main/MONOREPO.md) | [Apache-2.0](https://github.com/TerriaJS/terriajs/blob/main/LICENSE.md) 원문 확인. 복제·변경·NOTICE 등 조건을 실제 도입 시 검토해야 함. 이번 코드는 차용 없음 | 데이터 설명과 출처를 레이어에 연결, 도메인 계산과 UI 분리. 플랫폼 전체 도입 없음 |
| [uMap](https://github.com/umap-project/umap) | Django+Leaflet. `umap/models.py`, `views.py`, `storage`, `static`, `templates`, `tests`가 분리됨. 지도 생성, 데이터/레이어 편집과 지도 공유·임베드가 중심. [README](https://github.com/umap-project/umap/blob/master/README.md) · [사용자 문서](https://github.com/umap-project/umap/blob/master/docs-users/index.md) | [LICENSE](https://github.com/umap-project/umap/blob/master/LICENSE)는 **AGPL v3 또는 이후 버전**. API 메타데이터는 `NOASSERTION`이었지만 원문은 이 조건을 명시. 네트워크 제공까지 고려해야 하는 라이선스이므로 MIT처럼 취급하지 않음 | 지도 데이터와 화면/저장 책임 구분만 참고. 코드를 복제하지 않고 기존 React+Leaflet에서 자체 구현 |

**주의:** TerriaJS [기존 아키텍처 설명](https://docs.terria.io/guide/contributing/architecture/)은 페이지 자체가 version 8 반영이 부족하다고 경고한다. 예전 Knockout 구조를 최신 구현이라고 인용하지 않는다. 현재 파일 경로는 GitHub API에서 별도로 확인했다.

이 비교는 라이브러리 교체를 권하지 않는다. `prototype/package.json`에서 React 19, Leaflet/react-leaflet, Vite/TypeScript를 확인했고 현 저장소는 새 상태관리·라우터·차트 라이브러리를 금지한다. 기존 Vercel API 경로를 유지하며, **VWorld API**의 `edge`·서울 `icn1` 설정을 보존한다. AI `generate` 등 다른 경로에는 각 경로의 기존 실행환경 설정을 적용한다.

## 8. 구현 담당자에게 넘길 좁은 적용 제안

아래는 아직 구현 완료가 아닌 **설계 제안**이다. 기존 엔진·기능·데이터·빌드/배포 경계를 계승한다.

| 단위 | 적용 제안 | 대안과 반론 | 검증 |
|---|---|---|---|
| 사이트/앱 경계 | 공통 `SiteHeader/Footer`, 소개 페이지, 검토 앱을 책임별로 분리. 검토 상태는 화면 전환으로 언마운트되는 페이지보다 상위에서 유지 | 앱 전체를 새 프레임워크로 옮기면 재검증 범위가 커짐. 순수 소개 페이지 분리만으로 상태 소실 문제는 해결 안 됨 | 앱→소개→앱, 직접 주소, 새로고침, 뒤로가기에서 명세상 유지 상태 확인 |
| 경로와 기록 | 기존 스택 안에서 URL/History 기반 페이지 식별자를 두고 검토 상태·현재 후보·공통 입력·후보 조건을 구분 | 화면 링크만 바꾸는 구현은 새로고침/뒤로가기 요구를 빠뜨릴 수 있음. 브라우저 저장은 민감한 사업조건이 남는다는 의미를 결정해야 함 | 새 라우터 설치 없이 history/popstate와 배포 rewrite 경계 확인 |
| 계산 단일 경로 | `scoreSite()`·constants·pins·report/checklist·memoContext를 그대로 단일 기준으로 사용 | 페이지마다 계산하면 화면/비교/PDF가 어긋남 | 독립 기대값 15,000㎡·60억원을 각 표현에서 대조 |
| 현재 후보와 비교 후보 | 현재 선택을 분명히, 비교 담기/해제는 별도 행동. 후보 목록과 지도 상세를 같은 식별자로 연결 | 클릭할 때마다 자동 저장은 위치 확인만 하려는 사용자의 의도와 충돌 | 최대 4곳, 중복/추가/삭제/재선택, 각 후보 조건 복원 |
| 근거 상태 | ‘공개자료 확인’, ‘사용자 입력/확인’, ‘조회 중’, ‘미확인/실패’를 텍스트로 구분 | 녹/적 2색의 합격/불합격은 정보가 부족한 후보를 오판하게 함 | 실패 후 재시도와 이전 요청 취소, 색 없이도 상태 이해 |

기능 폴더 정리는 `site/`(공통 레이아웃·소개), `review/`(앱 화면·상태 연결)처럼 사용자 업무 책임 기준으로 제한하고, 기존 `scoring/compare/report/genai`를 불필요하게 다시 이동하지 않는 편이 낫다. 이 명칭은 제안이며 실제 import 영향·현재 구현에 따라 설계 담당자가 확정한다. 엔진까지 새 폴더로 옮기는 대규모 정리는 회귀 대비 편익이 작다.

### 다음 검수자에게 요구하는 반론

1. 미확인 사항을 앞세우면 사용자가 결론을 못 얻는다고 느끼는가? 그렇다면 점수로 덮지 말고 ‘다음 확인할 항목 3개’와 담당기관을 우선 정리하는 대안을 시험한다.
2. 첫 화면에 설명이 늘어 앱 진입을 늦추는가? 시작 버튼과 실제 결과를 첫 화면에 두되 프로젝트/팀 설명은 별도 페이지로 연결한다.
3. 4곳 비교가 390px에서 읽히는가? 후보별 카드와 항목별 비교 중 실제 수치 대조가 쉬운 방식을 검증한다. 가로 표 축소만으로 완료하지 않는다.
4. 출처와 경고를 모두 첫 화면에 두면 과밀해지는가? 중요한 미확인·제약은 요약, 상세 근거는 펼침으로 두되 PDF에는 필요한 근거가 빠지지 않게 한다.
5. 법무팀 경험이 주 사용자와 다른데 문제 정의가 설득력 있는가? 법무 경험은 제작 동기, 개발/사업검토 담당자는 실사용자라는 관계를 명확히 하고 실무 효율은 후속 검증 대상으로 둔다.
