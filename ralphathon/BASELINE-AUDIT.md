## 3. 우선순위와 구체적 공백

### P0: 완료 판정을 막는 공백

1. **메인·제품소개 경로가 없다.** `App.tsx`는 바로 데이터 전체 로딩 후 지도 workspace를 표시한다. 목표 사용자, 기본 입력, 산출물, 공통 보고서 확장 맥락을 보여주는 진입 화면과 명확한 검토 시작 동선이 필요하다. 같은 앱 안에서 가벼운 메인과 검토 화면을 분리하면 새 라우터 없이 달성할 수 있다.
2. **요약의 우선순위가 점수 중심이다.** `ResultOverview`는 큰 등급·참고점수·산식·감점 설명을 먼저 보여주고, 실제 제약과 미확인·다음 행동은 아래로 밀린다. `review.overview`, `review.issues`, `evidence`, checklist를 계승해 ‘확인된 제약 / 미확인 조건 / 다음 확인사항’을 먼저 보여준다. 점수는 보조 상세로 보존한다. 상세 미입력을 정상적인 기본 검토 상태로 설명하되 실제 공급조건의 미확인을 숨기면 안 된다.
3. **현재 통합 테스트는 사용 흐름을 증명하지 않는다.** 정적 마크업 테스트에는 실제 입력, 버튼 클릭, 비동기 조회, dialog 열기, 후보 재열기, 보고서 갱신, AI 생성 중 입력 변경이 없다. `memoContext` 해시 테스트만으로 MemoPanel의 무효화 완료를 주장할 수 없다. DOM 상호작용 테스트와 실제 브라우저 검증을 추가해야 한다.
4. **최근 운영·성능·접근성·인쇄·재현 증거가 없다.** 이 감사에서 Lighthouse/axe 보고서나 새 PDF/녹화/포스터/발표자료를 확인하지 않았다. 과거 문서상의 375px·5장 PDF·Ready·HTTP 200을 이번 390px/최종 빌드 검증으로 재사용하면 안 된다.

### P1: 구현·보안 단계에서 먼저 처리할 문제

5. **오래된 검색 응답이 최신 선택을 덮을 가능성이 있다.** `SiteSearch.tsx:99`에서 새 온라인 검색을 시작할 때만 이전 요청을 중단한다. 검색 중 지도 선택·읍면동 선택·좌표 선택·입력 변경에는 중단/요청 세대 검사가 없고, `:104` 응답 직후 `onPick` 한다. 지연 geocode 뒤 지도/읍면동을 선택하는 재현을 추가하고 최신 의도만 반영하도록 수정한다. 빈 입력은 `:64`에서 조용히 반환하므로 짧은 안내와 status/alert를 추가하는 것이 좋다.
6. **부가기능 실패가 전체 앱을 막는 경로가 남아 있다.** `useAppData.ts:90`의 Promise.all에서 `cases.csv`, `dc_stats.json` 등도 필수 요청이다. 참고 사례 하나의 500이 전체 오류 화면으로 이어질 수 있다. 핵심/선택 데이터를 명시하고 선택 실패를 ‘자료 미확인’으로 격리한다. 규제처럼 판단에 영향을 주는 자료를 빈 배열로 대체하고 ‘없음’으로 해석해서는 안 된다. 잘못된 optional JSON 구조도 범위에 맞게 검증해야 한다.
7. **원문 업스트림 오류가 사용자 응답으로 돌아간다.** `_vworld.ts:59`는 오류 본문 300자, `wms.ts:96`은 1,500자를 반사하며 geocode/zoning의 catch가 이를 사용자 응답에 붙인다. `generate.ts:124`도 OpenRouter 오류 본문을 반사한다. 실제 비밀정보 노출을 관측한 것은 아니지만, 키가 붙은 업스트림 요청의 오류 원문을 그대로 공개하는 경로는 제거해야 한다. 사용자 응답은 고정된 오류 코드/설명으로 제한하고, 회귀에서 가짜 비밀 문자열이 출력되지 않는지 검사한다.
8. **AI API 입력·스트리밍 예외 처리가 부족하다.** `generate.ts:73`의 `req.json()`은 예외 처리 없이 읽고 타입 단언만 한다. `prompt`가 문자열인지, JSON 객체인지, 본문이 제한 크기인지 확정하지 않는다. 잘못된 JSON/null/object/array/초과 길이/공백을 명시적으로 4xx 처리해야 한다. 타이머가 응답 헤더 도착 후 해제되어 스트림 정지까지 제한하지 못하고, reader 오류/클라이언트 취소 수명주기도 보강 대상이다. 기존 무료 모델 fallback은 유지하며 자동 유료 전환하지 않는다.
9. **보고서 첫 장의 우선 행동이 실제 제약과 연결되지 않는다.** `ChecklistReport.tsx:103`은 `r.review.actions.slice(-2)`만 출력한다. 엔진 마지막 두 항목은 모든 부지에 붙는 설계·인입 경로 안내라 규제·재해·공급 미확인 등의 우선 행동이 첫 장에 나오지 않는다. 엔진의 제약/근거와 연결한 순서로 표시하고, 나머지는 상세에 남긴다. 주소만 입력하면 비용/면적 누락의 분량이 큰 것도 기본 보고서 위계에서 개선한다.
10. **접근성과 작은 화면 위험이 코드에 보인다.** combobox에 활성 option 연결(`aria-activedescendant`)이 없고 오류는 live 안내가 아니다. map 클릭 외 주소/좌표 경로는 있으므로 키보드 동등 경로로 명확히 제공한다. 모바일 검색 폭은 `100% - 135px`, 지도 컨트롤은 180px로 정의되어 겹침 가능성이 있다. 8~10px 회색 본문과 GS 오렌지 위 흰 작은 글자는 대비 실측이 필요하다. 색상은 브랜드 계열을 유지하되 텍스트/CTA용 명도를 조정한다. 판정은 axe·브라우저 실측으로 확정한다.

### P2: 성능·일관성과 기존 기능 보존

11. **진입부터 큰 자료와 지도를 동시 로딩한다.** `public/data` 16개 파일은 비압축 합계 11,231,178바이트다. 큰 파일은 보호구역 3.26MB, 가구 2.62MB, 인구 1.97MB, 지형 1.28MB다. App는 데이터가 모두 끝나야 제품 UI를 보여준다. 메인은 독립·경량으로 만들고 검토 진입 시 lazy import/자료 로딩, 먼저 접근 가능한 검색·상태 화면을 제공한다. 결과가 유효하려면 필요한 근거가 모두 도착해야 한다는 원칙은 유지한다. 세부 최적화는 측정 후 수행한다.
12. **인근 필지 탐색은 유효 기능이지만 자동 실행/표현을 다듬어야 한다.** `useNearbySites`는 좌표 선택마다 실행된다. `api/nearby-sites.ts`는 중앙 1개+3단계 각 8개, 최대 25개 부분 구역을 조회하고 각 구역 첫 1,000개까지 본다. ‘15km 전체 탐색’이나 사업 적합 추천이 아니다. 기존 기능을 삭제하지 말고 별도 선택 실행과 ‘면적 기준 인근 후보 탐색’으로 표현하는 안을 권장한다. 부분 범위·도형 추정면적·권리/접도 미확인을 계속 표시한다.
13. **문서가 실제 데이터와 다르다.** `docs/DATA.md` 마지막은 인근 DC 2곳이라고 하지만 현재 `public/data/data_centers.json`은 32곳, asOf `2026-09-08`의 일부 목록이다. 이 32곳의 신규 전수 사실검증을 했다는 뜻은 아니다. 기존 데이터·출처·분류를 보존하고 문서를 현재 번들과 맞춰야 한다. AGENTS의 런타임 API 목록에도 이미 구현된 `nearby-sites`가 누락되어 있다.
14. **미사용 코드와 CSS가 혼재한다.** `CompareTray`, `ProjectScalePicker`, `ScoreCard`는 호환 re-export이며 현재 App의 직접 사용은 없다. 별도 `components/NumberField` 및 numberInput 테스트는 BusinessInputs 내부 숫자 입력과 다르다. 따라서 기존 숫자 parser 테스트가 현재 입력 UI의 회귀라고 볼 수 없다. `App.css`, 기본 React/Vite 자산도 직접 사용 근거가 없다. 전체 삭제/이동보다 사용 경로를 명시하고 새 코드를 작은 구조로 추가한다. 후속 정리는 import·빌드 검증 후 제한적으로 수행한다.

- 경로는 제안이며 디자인/구현 에이전트의 순차 반론 후 총괄이 확정한다. 새 framework·라우터·상태관리·차트는 필요 없다.
- 메인과 앱은 직접 열 수 있고 재측정 가능한 URL을 갖도록 한다. hash 또는 얕은 History API로 구현 가능하다. 현재 `base:'./'`와 상대 `data/...`는 경로 분리 시 깨질 수 있으므로 자산/API 경로와 새로고침을 확인한다.
- 기본 흐름: 메인 → 주소/지도 → 제약·미확인·다음 행동 → 선택 상세 → 비교 → 현재 후보의 보고서/PDF. 비교에서 후보를 열어 보고서를 바로 볼 수 있게 한다. 4개 후보 동시 PDF는 현재 목표에 명시되지 않으므로 필수 기능으로 확대하지 않는다.
- 보고서의 기본 출력과 AI 버튼을 시각적으로 분리하고, AI 실패 시 ‘기본 보고서 계속 사용’이 항상 드러나게 한다. 근거가 바뀌면 비교/화면/보고서가 같은 엔진 결과를 사용한다.
- 기존 브랜드 변수 `--brand:#d65f14`를 출발점으로 삼는다. 대비를 검증하고 GS 오렌지 주색을 유지한다.
- 공개자료·합성 조건만 시연한다. 근거·가정·미확인을 구분하며 실제 한전 공급 MW, 인허가 확정, 사업성/절감률을 새로 추정하지 않는다.

## 6. 다음 에이전트 인계

1. 디자인·사용흐름 에이전트는 이 문서의 2~4절과 목표/기준을 읽고, Paces/Felt/getdesign.md 비교를 통해 화면 위계를 제안한다. 기존 검색·상세조건·4후보·보고서·32곳 DC·인근 필지 탐색 기능을 소실시키지 않는다.
2. 별도 반론 검수는 ‘입력 부담을 낮추면서 미확인은 숨기지 않는가’, ‘사업 적합 추천처럼 읽히지 않는가’, ‘보고서가 AI와 무관하게 발견되는가’, ‘모바일에서 검색/결과/다음 행동이 이어지는가’를 확인한다.
3. 개발은 메인/검토 분리 → 근거 중심 요약/보고서 동선 → 검색 경쟁·선택 실패 격리 → API 안전 처리 순으로 작은 diff를 만든다. 산식·공통/개별 상태·서명 규칙은 유지한다.
4. 검증 에이전트는 P1 발견의 재현과 5절 시나리오를 독립 실행한다. 코드가 있어 보인다는 이유로 통과 판정하지 않는다.

**감사 결론:** 계산·자료·비교·기본 보고서는 재사용할 기반이 충분하다. 이번 목표의 주된 개발은 제품 진입·정보 위계·실패 처리·실제 흐름 검증이며, 배포와 제출물의 직접 증거를 새로 만드는 작업이 남아 있다. 현 시점 전체 완료 판정은 불가하다.
