/goal GS건설의 데이터센터 후보 부지 검토를 돕는 “여기 DC 돼요?”를 완결된 웹서비스로 재구성하고, 검증·Vercel 배포·해커톤 제출 자료까지 완성하라.

## 1. 문제와 사용자

주 사용자는 GS건설에서 데이터센터 개발·사업검토를 담당하는 실무자다. 후보지를 제안받을 때 전력·인허가·재해·주변 현황을 각각 찾아 비교하고 보고해야 하는 부담을 줄인다. 사용자가 “확인된 제약, 미확인 조건, 다음 확인사항”을 파악하여 후속 조사할 후보를 추릴 수 있게 하라. 그룹 내 확장은 공통 보고서 활용으로 설명한다.

## 2. 완료 상태

- 저장소 `https://github.com/seungminyi-byte/Camp_It_Ralph`의 `prototype`과 현행 지침·코드를 확인하고, 기존 계산 엔진·데이터·유효한 기능을 계승해 새 사용 흐름과 화면을 구현한다.
- 메인·제품 소개 → 주소 검색/지도 선택 → 기본 검토 → 선택적 상세조건 입력 → 최대 4곳 비교 → 근거와 다음 행동이 담긴 보고서·A4 PDF까지 연결한다. 내부 사업정보나 AI 없이도 기본 검토와 보고서를 사용할 수 있어야 한다.
- 공개 유사 서비스·GitHub 프로젝트를 조사해 채택 근거와 라이선스를 기록하고 디렉터리 구조를 정리한다. Paces([https://www.paces.com/](https://www.paces.com/)), Felt([https://felt.com/product)를](https://felt.com/product\)를) 참고하고, [https://getdesign.md](https://getdesign.md) 에서 디자인 후보 3개를 비교·토의해 확정한다. 기존 GS 오렌지를 주색으로 사용한다.
- 공개 데모, 공개 GitHub 저장소, 3분 내외 데모 영상, 홍보 포스터, 최대 5페이지 발표자료와 5분 발표 대본을 완성한다. 영상은 배포 URL에서 실제 조작을 녹화하고 Higgsfield 플러그인으로 편집한다. 플러그인을 사용할 수 없으면 실제 녹화 기반으로 완성하고 대체 사실을 기록한다.

## 3. 완료 확인 기준

- 주소만 입력한 검토, 상세조건 변경, 후보 추가·삭제·4곳 제한, 비교·보고서 갱신을 자동 테스트와 실제 브라우저에서 확인한다.
- 정상·빈 입력·잘못된 숫자·자료 결측·조회 실패·AI 실패를 검증한다. 입력이나 근거가 바뀌면 기존 AI 의견은 무효화하고, 실패한 부가기능이 가능한 기본 기능을 막지 않게 한다.
- 대표 계산을 검증한다: 연면적 30,000㎡·용적률 200%·건폐율 50%·4층이면 최소 대지 15,000㎡, 평균 차입잔액 1,000억원·연 6%·12개월이면 금융비용 60억원이다. 미입력과 명시적 0을 구별한다.
- 타입 검사·린트·전체 테스트·데이터 검증·프로덕션 빌드를 통과한다. 390/768/1440px 화면, 키보드 조작, 실제 A4 PDF의 모든 페이지를 확인한다.
- 개발 품질 목표는 Lighthouse 모바일 성능 90+, 접근성·Best Practices 95+, 핵심 화면 axe Critical·Serious 0건이다. 메인과 앱을 동일 조건에서 각각 3회 측정해 중앙값과 보고서를 남긴다. 의존성·비밀정보 노출·입력 처리의 보안 문제를 검사하고 발견한 높은 위험을 조치한다.
- 새 폴더에서 설치·빌드·실행을 재현한다. 배포 커밋·Vercel Ready·실제 화면과 핵심 API 응답을 확인하고, 데모·영상·저장소는 비로그인 환경에서 내용과 동작을 검증한다.

## 4. 제약

공개자료와 합성 시연 데이터를 사용하고 실제 사내자료·비밀키를 공개하지 않는다. 기존 스택과 계산의 단일 기준을 유지하며 사용자·팀원의 변경을 보존한다. 로그인·결제·협업 백엔드와 대규모 신규 데이터 수집은 제외한다.

공급 가능량·인허가·사업 적합성이나 측정하지 않은 절감 효과를 단정하지 않는다. 확인된 사실·가정·미확인을 구분한다. 중복되고 긴 면책문은 줄이되 “스크리닝 참고용, 한전 공식 검토·법률 판단 대체 불가”와 필요한 출처·자료 한계는 유지한다.

## 5. 판단 범위와 에이전트 운영

- 총괄 아래 기획·조사·자료정리·디자인·개발·보고서·테스트·검증·검수·수정·디버깅·보안·배포·포스터·영상·발표자료·완료보고를 별도 에이전트에 맡긴다. 세부 작업마다 새 하위 에이전트를 활용하고 필요한 문맥과 산출물만 인계한다.
- 기본적으로 총괄 외 실행 에이전트는 한 번에 하나다. 이전 작업의 완료·검수·인계 후 다음 작업을 시작한다. 총 예상 소요가 15시간을 넘을 때만 근거를 기록하고 파일·의존성이 분리된 작업을 제한적으로 병렬화한다.
- 중요한 범위·설계·디자인 결정은 관련 에이전트가 순차적으로 대안과 반론을 검토하고 총괄이 결론을 기록한다. 일반적인 제품·기술 선택은 사용자에게 묻지 않고 결정한다.
- 기존 권한 안의 코드·문서 수정, 검사, 작업 브랜치·PR을 통한 반영, GitHub·Vercel 공개 데모 배포와 시연물 공개를 수행한다. 신규 결제·권한 확대·파괴적 변경·대회 최종 제출은 별도 승인을 받는다. 필요한 승인을 에이전트 토의로 대신하지 않는다.

## 6. 검증 루프와 종료

GS·Team Attention의 행사 지침과 OpenAI 공식 Goal·Subagents 문서를 확인하고 실제 사용 가능한 모델·도구에 맞춰 운영하라. 모델은 정확성·속도·비용·도구 적합성으로 선택하고 실제 전환·위임만 기록한다.

“기준 확인 → 작은 작업 → 실행 → 별도 검증 → 실패 수정 → 재검증 → 인계”를 반복한다. 목표 원문, 단계별 완료 조건, 결정, 증거, 남은 일은 `ralphathon/`에 유지하고 새 에이전트는 이를 읽고 시작한다. 실제 주요 세션 JSONL과 추가 에이전트 로그를 보존하며 제출용 사본의 비밀정보를 점검한다.
