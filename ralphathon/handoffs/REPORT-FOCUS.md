# 보고서 포커스 수정 인계

2026-09-21 · 담당 `report_focus_hardening`

`ReviewWorkspace.tsx`의 보고서 진입/후보 복원/포커스 예약만 정리했다. 앞선 REPORT-FLOW 구현과 기존 미커밋 변경을 보존했다. 계산·보고서 모델·엔진·데이터는 변경하지 않았다.

## 현재 동작

- 현재 보고서 또는 후보 보고서를 클릭하면 선택과 저장 조건을 같은 React 갱신에서 복원하고 보고서를 연다.
- 포커스 요청은 `site`와 선택적 `pinId`를 가진다. layout effect가 현재 active·선택·후보·보고서 열림을 확인하고 단일 rAF에서 해당 보고서 ref의 제목으로 이동한다. cleanup이 이전 프레임을 취소한다.
- 홈은 render에서 비교창/보고서/요청을 초기화한다. 지연 홈 정리와 중첩 포커스 rAF는 없다.
- 일반 `openPin`도 보고서와 요청을 초기화하므로 같은 후보 조건 수정이나 다른 후보를 거쳐 복귀해도 이전 요청이 살아나지 않는다. 새 지점·제거·수동 접기·해제도 취소한다.

## 검증

ReactDOM/jsdom 상태 전환 **18개**, 수정 전 동일 테스트 **11 실패·7 통과**, 수정 후 전체 **22개 파일·218개 통과**. 타입·린트·프로덕션 빌드도 종료 코드 0. 자세한 범위, 독립 patch, 종료 코드·로그는 [RESULTS.md](../evidence/report-focus/RESULTS.md)에 있다.

이 검증은 실제 Chrome 검수가 아니다. 총괄의 지정 브라우저 연결 문제로 실제 UI 검수는 아직 남아 있으며 다음 PDF 단계의 통합 검수에서 홈/후보/조건 수정 전환과 키보드 포커스를 확인한다. 이 담당은 브라우저 제어·커밋·푸시를 하지 않았다.

## PDF 단계 유의사항

D013과 [REPORT-FLOW](REPORT-FLOW.md)의 같은 view-model·현재 서명·작업 토큰·활성 화면 대조 규칙을 유지한다. 이번 `reportFocusRequest`는 DOM 포커스 목적이며 다운로드 완료 여부나 파일 저장 권한을 나타내지 않는다. 실제 PDF 생성기에 이 포커스 요청을 다운로드 상태로 재사용하지 않는다.
